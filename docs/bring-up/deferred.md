# Deferred minors

What the review rounds of milestones 0–7, the latency follow-up, watchdog A and B and the panel drain left
for later, and what happens to each. **fix now**: this hardening pass fixes it (the task is named).
**fix later**: worth doing, not now (the reason says when or why). **won't fix**: the reason says why.

## Boot and the card
- A fatal error that begins on another thread between a save's check and its claim of the card still races the rescue's mount (`FATAL_THREAD` is read, then acted on) — **fix now (T4)** — check and claim become one step under the `Board` mutex.
- `show_led` can overwrite the solid-on-fatal LED while a pool thread's fatal error is rescuing — **fix now (T4)** — `show_led` writes only if no fatal error has begun.
- The stall's save can use the card beside a pool save that runs longer than its wait — **fix now (T4)** — it claims the card through the `Board`, and a non-fatal claimant gives up after `CARD_LOCK_WAIT`.
- The way out can restart the board under a pool save that had not started when it began, or race a save held longer than `CARD_LOCK_WAIT` (the queued-save flag covers only saves not yet started) — **fix now (T4)** — the way out claims the card and keeps the claim through the restart.
- The config parser puts an unknown key's text into the log without a length cap — **fix later** — only a key name, never a value; cap it the next time config errors are touched.
- A TOML syntax error reports line and column only, and `Section::section` does not join the parent path — **won't fix** — the first is deliberate (the parser's excerpt can quote the passphrase), the second is right while sections nest one level.
- A config test uses an address outside the documentation ranges for the gateway that lies outside the network (config.rs:1434, :1436) — **fix now (T6)** — one literal moves into 198.51.100.x.
- The config accepts a prefix with leading zeros, the network or broadcast address as address or gateway, and a bare `https://` list entry — **fix later** — each needs a spec decision first.
- The restore's shrink case leaves "backup plus old tail" if `set_len` or `sync_all` fails, a power cut mid-write leaves the old length under new leading bytes (inferred, never tried on real FAT), and the doc does not say a write error can leave config.txt partly written — **fix later** — needs a power-cut rig on the board; the window is milliseconds.
- The card's backup is not checked for a BOM, an `include`, or a lone carriage return that could hide the `os_prefix` line, and the parent directory is not fsynced after config.txt is created — **won't fix** — firmware syntax has none of these, deploy is the primary guard, and every restore ends with a sync and the unmount.
- The module table parser takes a tab-only line as blank, trims fields, and takes an empty argument without `--` as a module name — **won't fix** — leniency on the board's own table, never reached with such input.
- Boot-code tests are missing or loose: config accept-side boundaries (63-character hostname, /1, /30, 8- and 63-character passphrase), the module table's malformed-line and cycle tests assert only the line number, a read error other than not-found on config.txt, the `Reader::open` failure path, `serve`'s loop (save at a join, save-clock reset), the `REOPEN_EVERY` retry, and the start-order test that has no panel stand-in — **fix later** — test-only.
- Several boot tests are timing-dependent or collide: wait tests with wall-clock lower bounds, a loose zero-timeout bound, a logbuf timing assertion, kmsg temp files named by PID only — **fix later** — can fail on a loaded host; move to paused time and unique names.
- Log buffer and kernel-log polish: `dropped()` counts evictions of lines already taken, multi-line messages share one prefix, `kmsg` `read_records` discards what it read when a later read fails, unparsable records and a foreign logger are skipped silently, lines taken before `append_log` are lost if it fails, a fatal message with no logger goes nowhere, and `libc` serves `O_NONBLOCK` beside `rustix` — **fix later** — cosmetic or rare, boot diagnostics only.
- Taken log lines stay in memory until evicted, and the cap bounds text, not allocation overhead — **won't fix** — bounded at the cap.
- `fatal` writes a bare line without stamp or level when the log lock is held, which the QEMU ERROR/WARN helper cannot see — **fix later** — T4 rewrites this lock path; re-check after it.
- A fatal error in the first steps of boot has no watchdog behind its restart — **won't fix** — ruled: the watchdog is armed after the restore on purpose, and a refused restart of PID 1 is not realistic.
- A board without `wlan0`, or with a key that cannot be derived, reboots about every 110 s while powered — **won't fix** — that is the spec's 90 s no-association rule.
- `start_network`'s first stretch (route socket, loopback up, address) stays on the runtime thread and can run up to 10 s after the first pet — **won't fix** — bounded under the 15 s watchdog and before DNS serves; H1 leaves it inline on purpose.
- A burst of kernel lines is written to the console on the runtime thread at boot and can pass ~1 s once other futures share the thread — **fix later** — boot-only; needs a measurement on the board first.
- `init.rs` is about 4,200 lines (most of them tests) and step 10 (serve, the Wi-Fi component, address, leave) would fit a submodule — **fix later** — T5 adds tables only; a split is a separate move.
- A supervisor test comment says the Wi-Fi sender is dropped at 20 s (supervisor.rs:746; it is 10 s), the held-thread test never has a hold span the 90 s deadline, and a test comment over-claims what the card test proves — **fix later** — wording and one test. (The `sys::reboot` comment about the watchdog backing a refused restart is gone: it now says nothing does before the watchdog starts.)
- The main loop pets twice back to back, the wait helper's doc overstates the budget, and `fatal`'s re-entry guard assumed one thread (m0) — **won't fix** — (gone) the loop was rewritten under the supervisor and `fatal_entry` with `FATAL_THREAD` covers several threads.
- `rescue`'s early return skipping the unmount, and `Upstreams::with`'s IPv4 guard being a `debug_assert` (m0 and m2 part 1) — **won't fix** — (gone) `rescue` now mounts only when it has something to do, and the guard is an `assert!`.
- SNTP: untested branches (clock already within 500 ms, second server answers), one WARN gate for "no server answered" and "clock could not be set", redundant test imports — **fix later** — test and log polish.
- SNTP re-sends `synced` as true every hour and wakes waiters that already saw it — **won't fix** — a wake of a satisfied waiter is harmless.
- `serve` repeats the `log_to_sd` guard that `save_log_if_asked` already has and takes the log lock every tick even when `log_to_sd` is off — **won't fix** — one uncontended lock a second.
- The LED goes to Serving before the address is set and stays so if the configure fails (the brief's order) — **fix later** — re-check against the supervisor's single LED owner; it may be gone.
- A panic in the non-essential panel restarts the board (the panic hook makes any panic fatal) — **won't fix** — ruled and documented in the supervisor: the panel's code returns errors by design.
- The CPU governor write opens its file with `truncate(true)`, beyond the brief — **won't fix** — a no-op on sysfs, as its comment says.
- `join_cfg` runs PBKDF2 inline on the runtime thread and the nonce `getrandom` blocks until seeded — **won't fix** — tens of ms once, and the pinned kernel seeds within about a second of boot.

## Wi-Fi
- brcmfmac answers an nl80211 or rtnetlink command inside `sendmsg(2)`, holding the runtime thread up to about 2.5 s per firmware command (final review of m1; m4/5 ruled it stays) — **fix now (T1)** — the Wi-Fi component's netlink sockets send from a dedicated thread.
- With `speed.runtime_cpu` set, a `std` thread created from the runtime's thread starts with its one-core mask (the pool's threads leave it as they start; the `nl send` threads of T1 did not) — **fix now (T6c)** — `cpu::spawn_off_runtime_core` makes a named thread that has left the runtime's core, and the `nl send` and `tls handshake` threads are made with it; any later `std` thread made from the runtime's thread must be too.
- A radio that dies silently while joined leaves the status `Joined` and the 90 s rule never fires, because `hold` waits only for events (open item of the m4/5 review, again in m1's final recommendation) — **fix now (T2)** — `hold` queries the station every 10 s and three failures end the hold.
- `KernelRadio` is not reopened when `wlan0` goes away and returns with a new index — **won't fix** — T2's probe ends a silent hold and the 90 s rule restarts a board that stays dead (ruling R2-2).
- Doc polish in the radio and netlink layers: `Route::set_address` overstates REPLACE, `Message::msg_type`/`flags` and `Bss::bssid`/`freq_mhz` lack docs, `SCAN_SSIDS` indexes with a bare literal, a connect status of 0 with no MAC reads oddly, `nest` panics opaquely on a short builder, and `join`'s doc (join.rs:327-328) says the station leaves only after a taken connect — **fix later** — wording and small asserts.
- Wi-Fi and netlink tests that are brittle or missing: `KernelRadio`'s errno mapping (EBUSY/EAGAIN to Busy, ENOTCONN to success), the CAP_ACK test's exact 20-byte payload, `testns`'s "1 passed" substring match, `count()` loops that hang instead of failing, `LinkSocket::open(9999)` asserting only an error, no test that a no-signal BSS sorts last, no negative test of the "passphrase may be wrong" hint, the route socket's drop on a configure error, and one test helper built by hand beside `route::get_link` — **fix later** — test-only; one line each.
- Netlink `recv` cannot see a datagram over 32 KiB being cut (no `MSG_TRUNC`), so a big nl80211 dump would end as a timeout — **fix later** — not seen with one access point's scan; T1 touched the file and left this.
- Netlink details that stay: `attr_str` copies an SSID unwiped, `Attr` and `Message` derive `Debug` and print raw bytes, `events()` may return an empty Vec, `shrink_to_fit` reallocates each datagram — **won't fix** — no key is in the copy, the derive was brief-mandated and received messages are never Debug-formatted (`NETLINK_CAP_ACK` caps echoes), callers loop, and replies are rare and small.
- Link and join details that stay: the packet socket carries its protocol for a moment before `bind`, an EAPOL frame cut at 2,048 bytes is not noticed, duplicate BSSIDs in one scan are not merged, a late `ScanDone` can end the next scan early, a nonce is drawn per EAPOL frame, a tolerated RSNXE warning is not logged on a refused key, the retry loop's failed list is mutated in two places, the fake radio's helpers are `pub`, a fixture BSSID is made up — **won't fix** — brief-mandated, harmless, bounded or fixture-only; a cut EAPOL frame fails its parse anyway.
- `sys::packet_socket` accepts interface index 0, which binds to every interface (sys.rs:228) — **fix now (T6)** — refuse it as invalid input.
- A scan candidate with no signal logs "-21474836 dBm" (wifi/mod.rs:143, :175; `dbm` of `i32::MIN`) — **fix now (T6)** — log "no signal".
- The panel's and status page's signal falls back to the join's figure until the live reading is known, and `link_status` turns a join with no signal (`i32::MIN`) into -128 dBm through `held` (wiring.rs:298) — **fix later** — show no figure (`None`) for it; found with the log fix above.
- The hwsim ring leaves hostapd running in a dead namespace when a test is killed at its limit, and the rejoin test accepts any status after the kill — **fix later** — needs a process group and a stricter assertion; ignored tests.
- The signal cache is not cleared on a status change (a quick re-join shows the old association's figure for up to 5 s), and a failed `/proc/net/wireless` read is not logged — **fix later** — cosmetic and bounded.
- The live signal needs `CFG80211_WEXT` in the kernel; without it the join's figure shows and never updates — **fix later** — only the board can show it.
- `wifi: joined`/`wifi: associated` and `link lost`/`association lost` say the same thing twice — **won't fix** — the bring-up checks read both.
- A configure retry that keeps timing out stalls the Wi-Fi future up to 4 s every 30 s, and the biased tick can run one redundant configure with a duplicate `net:` line — **won't fix** — bounded, idempotent, no watchdog risk; T1 only takes the route socket off the runtime thread.

## DNS and upstreams
- The DoT handshake waits behind list work on the blocking pool (wd-a) — **fix now (T6c)** — H8: the planned reason (a question falls back to UDP while a session connects) is false once `start_tls` has run, because the resolver never goes back to UDP (so that blocking port 853 cannot push a question out in the clear) and a question that finds no session up waits for one within its own 2 s; so each handshake now runs on a thread of its own named `tls handshake`, started per handshake, at most one in flight per connection (at most `MAX_RACED` = 4), with the pool still 5 and no second runtime; `HANDSHAKE_WAIT` still counts inside the handshake; a thread that cannot be started is that open's error, which the reconnect backoff takes.
- A dead non-preferred upstream is not asked while the preferred one answers, so its "does not answer" line comes only once it is asked — **won't fix** — accepted in the hedge design; sequential failover had the same blind spot.
- `sys::random_u64` falls back to clock noise on a `getrandom` error without saying so — **fix later** — log once; cannot happen after the pool is seeded.
- A stale exchange can overwrite a newer preferred upstream and log a false "does not answer" (m2 part 1) — **fix later** — check against the hedged exchange, which was rewritten since; a compare-and-set if it still holds.
- A permanently refusing upstream counts as healthy in `not_answering()`, and a TC-flagged refusal used as the fallback goes to TCP — **fix later** — edge cases of the fallback rule.
- The race leans on tokio 1.54 internals (ERROR-only readiness, budget-free `try_io`, `try_send` readiness) — **fix later** — re-run the refused-port, flood and resend tests on any tokio upgrade.
- DNS test gaps and hygiene: the TCP `Mismatch` arm and a stranger socket's wrong-ID answer over TCP are untested, one slow-loser case cannot fail, the 2-byte framing is coded three times, the DO test does not assert two queries, the offset test is tautological beside a second `utc_offset` atomic, a stale test subtracts 100 s from `Instant` and may underflow on a fresh host — **fix later** — test-only.
- The QEMU self-test reads a `/sys` file with `std::fs` on the runtime thread, logs its five lines together, `lo_comes_up` is `pub` where `pub(crate)` would do, and a `services.rs` comment overclaims about bind order — **won't fix** — debug-only, microseconds, no behaviour.
- A stale entry whose renewal finds no forward permit is not renewed again for the cache's 10 s gap — **won't fix** — pre-existing and bounded.
- `Listeners::addr` falls back to the unspecified address with port 0 silently, and the IPv4 bind guards in `dns::listen` and `status` are `debug_assert` — **won't fix** — the address is a constant and the fallback is never reached.
- A TCP client re-asking every few seconds can hold a connection slot indefinitely, and per-packet tasks outlive a dropped `serve` — **fix later** — LAN-only; add a per-connection total deadline.
- Tight time limits in the DNS timing tests — **won't fix** — they ran green repeatedly, also pinned to one CPU.
- A query in the roughly 1 ms between the address and the route being set can log `dns: no upstream answers` — **fix later** — read the timestamps against the route line on the board.
- The new `init: open files: up to 4096` line is not a QEMU condition — **fix later** — one condition in `one_shot_conditions`.
- The class-bit verdict was timed at 1.75 µs against 1.36–1.58 µs before on a busy host (watchdog A) — **fix later** — re-time on a quiet host against H5 before the next release.
- A latency file written by a build between the two latency-tool commits passes the strict compare — **won't fix** — no such file exists; the existing ones fail it as they should.
- An `xtask latency` test flaked once on a port race (watchdog A) — **fix later** — test-only, pre-existing.

## xtask, deploy and QEMU
- `fetch` replaces its outputs one by one, so a failed fetch after a pin bump can leave a mixed set — **fix later** — stage and move.
- `fetch` has no size cap before the digest check, and its fixed `.partial` names are created with `File::create` (follows a symlink, collides between concurrent runs) — **fix later** — hardening of a dev tool.
- `fetch` verifies a package by path and re-opens it to extract, and a path that appears twice in an archive is written twice — **won't fix** — own checkout, one user, pinned and digest-checked archives.
- Housekeeping in `fetch` and `build`: `ureq` default features pull gzip crates, the fixture helper panics without zstd, no test ties a pin's `file` to its URL, a repeat run touches directory mtimes, one test name promises more than it checks, `build` hides cargo's output on success (so the board crate's warnings), the test constant `INITRAMFS` shadows the real one, the cpio writer keeps type bits in a mode and accepts duplicate or `.`/`..` paths, `pins.rs` lists the fetched module files by hand beside the module table — **fix later** — hygiene on a dev tool with our own inputs.
- `build` writes through a symlinked `out/` that points outside the checkout — **won't fix** — own checkout.
- The QEMU image writer produces a subdirectory that `fsck.fat` faults — **won't fix** — test image only; Linux reads and writes it.
- QEMU survives if xtask is killed by a signal (the guard covers returns and panics) — **fix later** — a process group.

- The LED allow entry cannot tell "no LED in QEMU" from "wrong LED path", and "permanent with `log_to_sd` on" has a host test only — **fix later** — the board confirms the first; add a scenario for the second.
- `qemu.rs` (about 4,100 lines) and `deploy.rs` (about 5,500) are mostly tests — **fix later** — split the tests out; no behaviour change.

## Left by the hardening pass's own review

- When the fatal error's wait for the board's mutex runs out, only the lock-free record of its thread is set; the card claim and the LED read the board's copy, so a holder that lets go after 200 ms could let a save or a link LED in under the rescue — **fix later** — both readers fall back to the lock-free record; needs a mutex held for over 200 ms first.
- A panic inside a pool save's card work makes its own rescue wait the whole card wait (5 s of the watchdog's 15) for its own claim — **fix later** — a claim held by the fatal error's own thread counts as its own; it was so before the board too.
- `show_led` on the runtime thread sleeps one 5 ms poll when the board's mutex is busy for microseconds — **fix later** — a few `try_lock`s before the polling wait; only at link changes, never per question.
- Up to four TLS handshakes can run at once on threads of their own (the pool capped them at about two) — **fix later** — a process-wide limit of two, or a lower priority for the handshake thread, if the board shows a few ms of delay at boot or on reconnect.
