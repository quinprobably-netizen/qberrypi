# Milestone 1: the Pi joins Wi-Fi by itself

Date: 2026-11-10. Board: Raspberry Pi 3 Model B Plus Rev 1.4. Build 1794374458, deployed twice in a row with `cargo xtask deploy`, with nothing touched on the Pi in between.

## Result

It worked on the first attempt: Task 12 took one Pi boot and needed no fix. Both boots joined the network, set the address and default route, answered ping, ran for 120 s and came back as Raspberry Pi OS. The two logs differ only in timings of a few milliseconds.

| Time after init started | Boot 1 | Boot 2 |
|---|---|---|
| Kernel's share before init (`boot:` line) | 2.079 s | 2.075 s |
| `regulatory: country …, as configured` | 0.670 s | 0.693 s |
| `wifi: scan found …` | 3.542 s | 3.571 s |
| `wifi: associated with …` | 3.692 s | 3.728 s |
| `wifi: joined …` | 3.705 s | 3.741 s |
| `net:` address and default route set | 3.745 s | 3.766 s |
| `icmp: answered N of M echo requests` | 9 of 9 | 10 of 10 |

- The join itself, from association to an authorized port, takes 12 ms. Almost all of the 3 s before it is the scan.
- Power-on to an address on the network is about 5.8 s after the kernel starts.
- The joined band was **5 GHz** (channel 36), even though the 2.4 GHz radio of the same network was heard 8 dB stronger: the "prefer 5 GHz" rule works.
- The association request carried qberrypi's **own** RSN element, as reported back by the kernel in the connect event.
- The RSNXE warning (`RSNXE in message 3 differs …; tolerated`) did **not** appear. The mismatch that broke Raspberry Pi OS's supplicant came from the 2.4 GHz access point, which qberrypi did not join.
- The regulatory database was accepted and the configured country applied. None of the cfg80211 or brcmfmac failure lines appeared.
- `roamoff=1` was accepted (no `unknown parameter`). The CPU governor was `performance`.
- Neither log has a `WARN` or `ERROR` line, and neither holds the passphrase or the PMK. `deploy` did not refuse either log.

Back on Raspberry Pi OS after each boot, `config.txt` is byte-identical to `config.pios.txt`, and Pi-hole was listening and blocking.

## Different from the plan's Facts

- The kernel logs `power save enabled` when the interface comes up and then `power save disabled` when qberrypi turns it off; the plan expected only the second line.
- `deploy`'s count of pings answered while the Pi was away (9 of 11 and 10 of 13) cannot tell qberrypi's answers from Raspberry Pi OS's, since both use the same address. qberrypi's own `icmp: answered` line is the proof that it answered.

## Not measured

- Recovery from a lost link or a wrong passphrase on the real radio: those are covered on simulated radios only. Milestone 4's 90-second rule handles a radio that disappears.
- How long the brcmfmac netlink handlers hold the runtime thread when the firmware stops answering (up to about 2.5 s per command by the driver's source).
