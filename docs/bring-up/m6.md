# Milestone 6: cutover

Date: 2026-11-11. Board: Raspberry Pi 3 Model B Plus Rev 1.4. Build 1794456661 (commit 421a448).

## Rehearsal

A permanent deploy (`cargo xtask deploy --permanent`) was done once and undone before the real one:

- qberrypi answered 16 s after the restart and stayed selected across a pulled power cord;
- `cargo xtask return-to-pios --boot <mount>` on the card in a reader put Raspberry Pi OS back, and
  Pi-hole answered again on the next boot.

## Cutover

Before the deploy, on commit 1f56f10: 2097 tests pass, clippy and fmt are clean, and the 11 QEMU
scenarios hold. The configuration has every development switch off (`one_shot`, `log_to_sd`,
`return_after_secs`, no fault), DNS-over-TLS on and the runtime pinned to core 1, the configuration
measured in `latency-baseline.md`.

- `cargo xtask deploy --permanent`: the build answered 15 s after the restart.
- `cargo xtask probe --stage resolver`: 8 of 8 checks hold; `--stage blocker`: 15 of 15.
- After 95 s: 67 questions, 25 blocked, 32 sent upstream over TLS with 0 failures, 0 sessions closed
  by the server, 0 retries; no warning or error in the log; the longest runtime gap was 22 ms, during
  start-up.
- The desktop client logged in over HTTPS on port 443 against the pinned certificate and read alerts
  and devices; the devices seen so far were marked as known.

The Pi keeps the address the Pi-hole install had, so clients that already used it as their DNS server
needed no change.

## What a permanent qberrypi does not do

- It writes nothing to the card. Logs live in memory and are read at `/log`.
- It cannot be updated over the network in v1: an update is `return-to-pios` with the card in a
  reader, then a new deploy.
- It has no unencrypted fallback with DNS-over-TLS on: if no TLS upstream answers, forwarded
  questions fail, and cached and blocked ones are still answered. The board has no clock of its own
  and a certificate check needs one, so until SNTP has set it only the time servers' names are looked
  up in the clear; every other forwarded question waits for TLS or fails. A network that blocks SNTP
  therefore stops forwarding and leaks nothing. (The build named above, the one deployed at cutover,
  still forwarded over UDP until the clock was set, about 4.4 s after power-on; the pre-publish
  security review found that, and the fix is in the published tree.)

## Getting back

Pull the Pi's power cord (safe for qberrypi), put its card in a computer, run
`cargo xtask return-to-pios --boot <where it is mounted>`, eject the card and put it back.

## Known limits (from the pre-publish security review)

- The TLS code is `rustls` with the pure-Rust `rustls-rustcrypto` provider, a pre-release that has had
  no audit. It was chosen to keep the image free of C; treat it accordingly.
- SNTP is unauthenticated: someone on the path can set the clock wrong, which makes certificates
  look expired and stops forwarding and list refreshes until the next good answer. It cannot make
  a question go out in the clear.
- New-device alerts are capped at 20 an hour for each kind, and the count of suppressed ones is
  shown instead; a flood of invented devices can hide a real one in that hour.
- Devices heard in the first ten minutes after a start with no known list pushed are taken as
  known, and nothing is kept across restarts: the desktop client pushes the list again.
- The status page on port 80 needs no login and shows the build, uptime, counters and the log,
  which names the access points' addresses. It shows no client address and no name asked for.
- The API, the TCP listener and the forward slots have small fixed limits and no share for each
  client, so a device on the home network can crowd the others out of them. UDP answers from the
  cache and the block set are not affected.
