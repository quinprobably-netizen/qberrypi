# Milestone 1 (Wi-Fi) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** As PID 1 and with no other program, qberrypi joins the configured WPA2 network on the Pi's own radio, takes its static address, and answers ping.

**Architecture:** An in-tree netlink layer (pure message builders and parsers, a small async socket) talks route netlink and nl80211. The Wi-Fi logic is written against a `Radio` trait, so scan, association, the `qb-wpa2` handshake, key installation, rekeys and the retry rules are tested on the development machine with a scripted radio and the IEEE reference handshake; one implementation of the trait drives the real kernel. Init keeps steps 1 to 9 as they are and then runs a single-threaded tokio runtime whose main loop pets the watchdog, drains the kernel log and saves the card log while the Wi-Fi future runs beside it.

**Tech Stack:** Rust stable, edition 2024. New in `crates/qberrypi`: `tokio` 1 (`rt`, `time`, `net`, `macros`, `sync`; no multi-thread runtime), `qb-wpa2` (path), `zeroize` 1, `rustix` features `net` and `rand`; for tests `hex-literal` and tokio's `test-util`. New in `xtask`: `qb-wpa2` (path). Test equipment on the development machine only: `unshare` (util-linux), `ping`, `hostapd` 2.12 and the kernel's `mac80211_hwsim`.

**Spec:** `docs/superpowers/specs/2026-11-10-qberrypi-design.md` — sections "Wi-Fi", "Network", "Boot sequence", "Failure handling", "Testing". Consumed interface: `docs/superpowers/plans/2026-11-10-qb-wpa2.md` (the Interfaces blocks of its Tasks 1, 2, 4, 6 and 7, and the caller's contract of its Task 10).

## Global Constraints

- Board: Raspberry Pi 3 Model B+ only. Kernel release pinned to `6.18.60+rpt-rpi-v8`.
- The initramfs contains exactly one executable, `/init`, and it never runs another program. `unshare`, `ping` and `hostapd` are run by tests and by `xtask` on the development machine, never by qberrypi.
- `unsafe` is allowed only in `crates/qberrypi/src/sys.rs`. That covers the crate's tests and `crates/qberrypi/tests/`.
- No passphrase, PMK, KCK, KEK, TK or GTK in any log line, error message, `Debug` output or committed file. Every netlink request buffer is wiped (`zeroize`) after it is sent, because two of them carry keys.
- The repository is public. Committed files use example values only: `example-network`, `192.0.2.0/24`, the IEEE sample addresses `a0:a1:a1:a3:a4:a5` and `b0:b1:b2:b3:b4:b5`. `docs/bring-up/m1.md` carries no network name, BSSID, MAC address, IP address or raw log.
- This milestone adds no kernel module (see Facts 1). If a task finds that one is needed after all, it is added in the same commit to `xtask/src/pins.rs` (`wanted`), to `qberrypi::modules::DEFAULT_TABLE`, and to the file lists the tests of `pins.rs` and `build.rs` pin.
- The one-shot restore stays the first write to the card: nothing this plan adds runs before step 4 of `init::run`, and Wi-Fi starts after step 9.
- The card is written only under `debug.one_shot` or `debug.log_to_sd`, each write followed by a sync and an unmount. Log saves are bounded: at the join, at most one every 30 s besides, and on the way out.
- Scope: WPA2-PSK, CCMP, no protected management frames, static IPv4. No DHCP, no IPv6, no WPA3.
- The runtime has one thread. Nothing on it blocks for longer than a card save does; every wait is a tokio timer or a socket readiness wait, so the main loop pets the 15-second watchdog at least every 5 s.
- Netlink is native-endian. The golden bytes in this plan are little-endian, which both the development machine (x86-64) and the Pi (aarch64) are.
- No netlink crate (`neli`, `netlink-*`, `rtnetlink`): see Decision 1.
- Gates, all clean before every commit: `cargo test --workspace`, `cargo clippy --workspace --all-targets` (no warnings), `cargo fmt --all --check`, `cargo build -p qberrypi --release --target aarch64-unknown-linux-musl`, and `grep -rln unsafe crates/qberrypi/src crates/qberrypi/tests` printing only `crates/qberrypi/src/sys.rs`. A commit that touches `init.rs` or `xtask/` also needs `cargo xtask build && cargo xtask qemu-test` with six `ok`.
- Implementers stage files by name (`git add <path>…`, never `-A` or `.`), end every commit message with a `Co-Authored-By:` trailer naming the model that wrote the commit, and never push. Implementers never contact the Pi: every deploy is run by the session lead.

## Review Focus

1. The access point's message 1 reaches the packet socket before the kernel reports the association (on this FullMAC driver the two travel different paths). It must be kept and answered once the association is known, not dropped. (Test in Task 7.)
2. The passphrase in `qberrypi.toml` is wrong. The access point repeats message 1 and deauthenticates. qberrypi must say "the passphrase may be wrong", back off to 30 s and keep trying, with nothing secret in the log. (Tests in Tasks 7 and 8.)
3. The network name is advertised only by, or also by, a network outside the scope (WPA3-only, PMF required, mixed WPA/WPA2). Each such BSS is skipped with its reason; when nothing in scope is left, each attempt says so. (Tests in Tasks 5 and 8.)
4. The radio does not cooperate: a scan is refused as busy, aborted, or never ends; the association never completes; the event socket overruns. Every wait has a bound and ends in a retry. (Tests in Task 7.)
5. Bytes from the kernel or from the air are malformed: a truncated attribute, an element list that overruns, an Ethernet frame shorter than its header. No parser may panic. (Tests in Tasks 1, 3, 5 and 6.)

## Facts

Gathered while planning; every later section argues from these.

1. **No module is missing for the regulatory database.** `modules.builtin` of the pinned kernel package lists `rsa_generic`, `cryptomgr`, `sig`, `akcipher`, `sha256`, `public_key`, `x509_key_parser`, `pkcs7_message` and `mpi`, and its config has `CONFIG_CRYPTO_RSA=y`, `CONFIG_CFG80211_REQUIRE_SIGNED_REGDB=y`. The Pi's `modules.alias` has no `crypto-pkcs1` or `crypto-rsa` entry. The request for `crypto-pkcs1(rsa,sha256)` that milestone 0 saw is the kernel's ordinary first step when it instantiates a template algorithm: it asks the module helper for the instance name, is told no, and then builds the instance from the built-in template (no request for `crypto-pkcs1` followed, and four certificates were then loaded). Those two helper lines will keep appearing and mean nothing. Running Raspberry Pi OS, the same Pi has only `rfkill`, `cfg80211`, `brcmutil`, `brcmfmac`, `brcmfmac_cyw` loaded and reports the global regulatory domain as the country its `cfg80211` was loaded with.
2. **What milestone 0 could not show** is whether the database was accepted: its kernel-log dump ended 0.43 s into the boot, before the asynchronous load. The kernel's failure lines are `cfg80211: failed to load regulatory.db` and `cfg80211: loaded regulatory.db is malformed or signature is missing/invalid`. `NL80211_CMD_GET_REG` returns the global domain: `00` if the database was refused, the configured country if it was applied.
3. **The chip's firmware gets the country from the driver's regulatory notifier**, which cfg80211 calls when the wiphy registers (`wiphy_regulatory_register`). Its failure lines are `Country code iovar returned err`, `not an ISO3166 code` and `Firmware rejected country setting`. The NVRAM file has no `ccode`.
4. **The firmware does not do the handshake.** `iw phy` on the Pi lists the extended features `CQM_RSSI_LIST` and `DFS_OFFLOAD` only: no `4WAY_HANDSHAKE_STA_PSK`. Ciphers: WEP, TKIP, CCMP-128, CMAC. Up to 10 scan SSIDs; scan flush supported. With the country applied, 2.4 GHz channels 1–11 and 5 GHz channels 36–165 are usable.
5. **`brcmfmac` in kernel 6.18.60** (`cfg80211.c`, read from the Raspberry Pi kernel tree):
   - `connect` needs the interface up, takes the BSSID and the channel, passes the RSN element of `NL80211_ATTR_IE` to the firmware, and reads `wpa_versions`, the first pairwise cipher, the group cipher and the first AKM suite. It leaves the firmware supplicant off unless a PMK is passed, which this plan never does.
   - Success is reported by `cfg80211_connect_done` with the association request and response elements, and the carrier goes on in the same call. Failure is reported as status 16. Data frames reach the packet socket by another path, so message 1 can arrive first.
   - `add_key` installs a pairwise key when a peer address is given and a group key otherwise, and takes a 6-byte receive counter in the byte order of the EAPOL-Key RSC field. `NL80211_CMD_NEW_KEY` is refused with `ENOLINK` before the association is reported. The default-key operation only acts for WEP.
   - `change_station` with the authorized flag sends the firmware's authorize command for that peer, in station mode as in any other.
   - `scan` is refused with `EAGAIN` while a scan runs or a connection is being made.
   - `set_power_mgmt` logs `power save disabled` in the kernel log.
   - The module parameter `roamoff=1` turns the firmware's own roaming off.
6. **The in-tree encoder works.** A 150-line prototype sent these to real kernels: on the development machine, the generic-netlink family lookup with multicast groups, `GET_REG`, an interface dump and a scan dump (with RSN and RSNXE elements found in it); inside an unprivileged user and network namespace, link up, address, default route, a link query, and a packet socket bound to ethertype `0x888e` that sent and received a frame. The kernel's error text arrived through extended acknowledgements (`Nexthop has invalid gateway`). All nl80211 commands this plan uses carry `GENL_UNS_ADMIN_PERM`, so they also work inside a user namespace that owns the radio.
7. **Things the prototype taught:** `rustix` has `SocketAddrNetlink` and safe `socket`, `bind`, `send`, `recv`, but no option setter for `SOL_NETLINK` and no `sockaddr_ll`; those need `libc`. Route netlink is protocol 0, which `rustix` spells `None`. A request that is neither a dump nor sent with `NLM_F_ACK` gets a reply with no end marker, so every request carries one of the two.
8. **The development machine** has `hostapd` 2.12 and unprivileged user namespaces; `mac80211_hwsim` is present but not loaded, and `/boot` is not readable, so a VM cannot borrow the host's kernel.

## Decisions the spec leaves open

1. **Netlink: in-tree, not `neli`.** The spec's spike was done while planning (Facts 6). `neli` would still need every nl80211 constant written by hand, its 0.7 interface differs from the one most examples show, and it hides the bytes the tests should pin. The in-tree layer is about 400 lines, pure where it encodes and decodes, and its messages are checked three ways: golden bytes computed independently from the kernel's structure definitions, a real kernel in a namespace, and the simulated radio.
2. **tokio arrives now**, as the spec's process model says, as a current-thread runtime. With one thread, `fatal`'s single-thread assumption still holds and no lock is needed around the card. The Wi-Fi logic is a future polled by the main loop's `select!`, not a spawned task, so it needs no `Send` bound.
3. **Regulatory gap: nothing to add, something to prove.** No module is added (Facts 1). Init reads the global regulatory domain after the driver is loaded and logs whether it is the configured country; QEMU checks that line against the real kernel, modules and database before the Pi does.
4. **Firmware roaming is off** (`roamoff=1`). qberrypi chooses the BSS itself, which is what "prefer 5 GHz" needs; a roam event that arrives anyway is treated as a lost link.
5. **Port control:** after the keys are installed, `NL80211_CMD_SET_STATION` with the authorized flag, as the reference supplicant does on this driver. A refusal is logged and the link is used anyway. The interface's link mode is left at the kernel's default, so the operational state follows the carrier. No `NL80211_CMD_SET_KEY`: it does nothing for CCMP here.
6. **The association request's RSN element** is taken from the connect event when the kernel reports one and handed to `qb-wpa2` as `own_rsne`; otherwise `SUPPLICANT_RSNE`.
7. **Backoff:** the wait before the next attempt is 0, 1, 2, 4, 8, 16, 30, 30, … seconds, counted over failures in a row. A link counts as a success only once it has held for 30 s; a link lost sooner is one more failure, so a network that accepts and then drops the station does not cause a tight loop.
8. **A BSS that just failed is tried after the others** with the same name, and the list of failures is forgotten when every candidate is on it or a link has held. Without this, a 5 GHz radio that refuses would be retried forever while the 2.4 GHz one stood by.
9. **Timeouts:** scan 15 s; association 10 s; handshake 10 s (the reference supplicant's value); none once the link is established. The supplicant never retransmits on its own: the access point repeats its message and `qb-wpa2` answers it again.
10. **The reboot after 90 s without an association** belongs to milestone 4 ("reboot policies"). In this milestone a boot that cannot join keeps trying until `debug.return_after_secs`.
11. **Address and route** are set by the main loop each time Wi-Fi reports a join, with replace semantics, so a rejoin puts them back if the kernel dropped them. `lo` is brought up at start.
12. **Proof of the ping on the Pi's side:** on the way out init logs the kernel's ICMP counters. `deploy` pings the configured address while the Pi is away and refuses a log that contains the passphrase or the PMK.
13. **Simulated radio: yes, but in a namespace, not a VM.** `mac80211_hwsim` is a SoftMAC driver and cannot show the FullMAC behaviours of Facts 5 (event order, the association request element, `EAGAIN` on scan, the firmware's country). Everything else is the same kernel interface: the encoding of every nl80211 command, the packet socket, the whole handshake against a real access point implementation, key installation, rekeys and rejoin. Each of those found on the Pi instead costs a boot that takes the household's DNS away for about two minutes. A VM needs a kernel image this machine cannot read and a second pinned userland for `hostapd`; a user and network namespace needs one `sudo modprobe mac80211_hwsim radios=0` from the owner and touches no real radio. The ring is Task 9, skippable: if the owner declines, the kernel radio is first exercised on the Pi.
14. **Kernel log:** read continuously into qberrypi's log from now on, so the driver's own messages about a failed join reach the card.

## Seams with the other plans

`2026-11-10-m2-m3-resolver-blocker.md` and `2026-11-10-m4-m5-resilience-panel.md` were written at the same time as this plan and run after it. What they lean on, and what this plan leaves for them:

- The three places in `init.rs` that the resolver plan edits keep their names and their jobs: `load_wifi_driver`, `pet_watchdog`, and `serve`, the loop that logs `returning`. `serve` is an `async fn` after Task 4.
- **Where the runtime lives differs.** This plan runs its runtime on PID 1's main thread, with the main loop and Wi-Fi as two futures of one `select!`. The resolver plan keeps the main thread synchronous and starts a `services` thread with a runtime of its own. The two fit together as written — its thread, its heartbeat check in `pet_watchdog`, its two-thread `fatal` and its card lock all still apply — and leave two runtimes until milestone 4's supervisor merges them. The session lead may instead move Wi-Fi onto the `services` thread when that exists; nothing in `wifi/` or `netlink/` cares which thread polls it.
- `LogBuf::text` (Task 7) has the signature both other plans give it; whichever plan runs second finds it there.
- `lo` is up after Task 4, so the resolver plan need not add `sys::loopback_up`.
- The default route appears in `/proc/net/route` when the `net:` line is logged; the resolver plan's SNTP task waits for exactly that.
- Wi-Fi's state leaves `init.rs` as a `tokio::sync::watch` channel of `wifi::WifiStatus` (Task 10). The resilience plan's `live::WifiStatus` is made from it: associated is `Joined`, the signal is `dbm(signal_mbm)`, the access point is `mac(&bssid)`.
- The reboot after 90 s without an association is the resilience plan's (Decision 10).
- Both other plans add tokio with a superset of this plan's features.

```rust
pub const NLMSG_ERROR: u16 = 2;      pub const NLMSG_DONE: u16 = 3;
pub const NLM_F_REQUEST: u16 = 0x001; pub const NLM_F_MULTI: u16 = 0x002; pub const NLM_F_ACK: u16 = 0x004;
pub const NLM_F_DUMP: u16 = 0x300;    pub const NLM_F_REPLACE: u16 = 0x100; pub const NLM_F_CREATE: u16 = 0x400;
pub const NLM_F_CAPPED: u16 = 0x100;  pub const NLM_F_ACK_TLVS: u16 = 0x200;   // in an acknowledgement
pub const NLA_F_NESTED: u16 = 0x8000; pub const NLA_TYPE_MASK: u16 = 0x3fff;

pub struct MsgBuilder { /* private Vec<u8> */ }
impl MsgBuilder {
    pub fn new(msg_type: u16, flags: u16) -> Self;          // 16-byte header; length and sequence are set by finish
    pub fn header(self, bytes: &[u8]) -> Self;              // the family's fixed header, padded to 4
    pub fn attr(self, ty: u16, payload: &[u8]) -> Self;     // length = 4 + payload; padded to 4 with zeros
    pub fn attr_u8(self, ty: u16, v: u8) -> Self;   pub fn attr_u16(self, ty: u16, v: u16) -> Self;
    pub fn attr_u32(self, ty: u16, v: u32) -> Self; pub fn attr_flag(self, ty: u16) -> Self;
    pub fn attr_str(self, ty: u16, text: &str) -> Self;     // with a terminating NUL
    pub fn nest(self, ty: u16, fill: impl FnOnce(Self) -> Self) -> Self;   // type | NLA_F_NESTED, length patched after `fill`
    pub fn flags(&self) -> u16;
    pub fn finish(self, seq: u32) -> Vec<u8>;
}
#[derive(Debug, Clone, Copy)]
pub struct Attr<'a> { pub ty: u16 /* flag bits removed */, pub payload: &'a [u8] }
impl<'a> Attr<'a> {
    pub fn u8(&self) -> Option<u8>;   pub fn u16(&self) -> Option<u16>;  pub fn u32(&self) -> Option<u32>;
    pub fn i32(&self) -> Option<i32>; pub fn mac(&self) -> Option<[u8; 6]>;
    pub fn str(&self) -> Option<&'a str>;       // up to the first NUL
    pub fn nested(&self) -> Attrs<'a>;
}
pub struct Attrs<'a> { /* private */ }          // Iterator<Item = Attr<'a>>; ends at the first attribute that does not fit
pub fn attrs(bytes: &[u8]) -> Attrs<'_>;
pub fn find<'a>(bytes: &'a [u8], ty: u16) -> Option<Attr<'a>>;
#[derive(Debug, Clone, Copy)]
pub struct Message<'a> { pub msg_type: u16, pub flags: u16, pub seq: u32, pub payload: &'a [u8] }
pub fn messages(datagram: &[u8]) -> impl Iterator<Item = Message<'_>>;   // ends at the first header that does not fit
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct NlError { pub errno: i32 /* positive */, pub message: Option<String> }
// Display: std::io::Error::from_raw_os_error(errno), then ": {message}" when there is one.
pub fn ack(message: &Message<'_>) -> Option<Result<u32, NlError>>;
// None unless msg_type is NLMSG_ERROR. The payload starts with an i32: negative is an error, zero or
// positive is success with that value. The kernel's text is attribute 1 after the echoed request:
// at payload offset 20 when NLM_F_CAPPED is set, else at 4 + the echoed request's own length.
```

Every integer is native-endian (`to_ne_bytes`). An attribute's length field counts its 4-byte header and its payload, not the padding.

`request` rules: the builder's flags must hold `NLM_F_ACK` or `NLM_F_DUMP` (Facts 7; `debug_assert`). It sends the finished message, wipes the buffer, then reads datagrams until the end marker for its sequence number, giving up after `REPLY_TIMEOUT`. Messages with another sequence number are skipped. With `NLM_F_DUMP` the end is `NLMSG_DONE`; otherwise it is the acknowledgement. An error acknowledgement ends either kind with `Kernel`. The payloads of all other messages are returned in order. The receive buffer is 32 768 bytes. `NLM_F_DUMP_INTR` is ignored.

Message layouts (the fixed header, then the attributes in this order):

| Builder | Type, flags | Fixed header | Attributes |
|---|---|---|---|
| `get_link` | 18 `RTM_GETLINK`, `REQUEST\|ACK` | 16 zero bytes | 3 `IFLA_IFNAME` string |
| `set_link_up` | 19 `RTM_SETLINK`, `REQUEST\|ACK` | `ifinfomsg`: family 0, pad, type 0, index (i32), flags 1, change 1 | — |
| `new_address` | 20 `RTM_NEWADDR`, `REQUEST\|ACK\|CREATE\|REPLACE` | `ifaddrmsg`: family 2, prefix length, flags 0, scope 0, index (u32) | 2 `IFA_LOCAL`, 1 `IFA_ADDRESS`, 4 `IFA_BROADCAST`, 4 bytes each |

`parse_link` reads the index at payload offset 4 (i32), the flags at offset 8, and attribute 1 `IFLA_ADDRESS` after the 16-byte header; a link without a 6-byte address gets `[0; 6]`.

   - `Overrun` or an error → `Radio`; other events are ignored; the deadline → `AssocTimeout`.
3. Log `wifi: associated with …`. `own_rsne` is `ies::element(&req_ies, EID_RSN)` if there is one, else `SUPPLICANT_RSNE`; when it differs from `SUPPLICANT_RSNE`, log `wifi: association request carried its own RSN element {hex}`. `Supplicant::new(Params { pmk: cfg.pmk.clone(), aa: bssid, spa: radio.station(), ap_rsne: candidate.rsne, ap_rsnxe: candidate.rsnxe, own_rsne })` → `Handshake(e)`.
4. Until `HANDSHAKE_TIMEOUT` after step 3, take the kept frames first, oldest first, then events:
   - `Frame(f)`: `eapol::parse`; ignore it unless the ethertype is `ETHERTYPE_PAE` and the source is `bssid`. Take `radio.nonce()` (→ `Radio`), then `supplicant.handle(body, || nonce)`:
     - `Err(HandshakeError::RsneMismatch)` → `Handshake(RsneMismatch)`;
     - any other `Err(e)` → log `WARN wifi: dropped a handshake frame: {e}` and go on;
     - `Ok(reply)`: `send_frame(build(bssid, station, ETHERTYPE_PAE, &reply.frame))` — an error is logged as a warning and the handshake goes on, since the access point repeats its message; log `wifi: sent handshake message 2` or `4`. Then, in this order: `reply.tk` → `install_pairwise(bssid, tk)` → `KeyInstall(e)` on error, log `wifi: pairwise key installed`; `reply.gtk` → `install_group` → `KeyInstall(e)`, log `wifi: group key {id} installed`; `reply.warning` → the RSNXE warning line. If `reply.kind` is `Message4`: `authorize(bssid)` — log `wifi: port authorized`, or a warning with the error — and return the `Link`.
   - `Nl(Disconnected { reason, by_ap })` → `Disconnected` with `phase: Some(supplicant.phase())`;
   - `Overrun` or an error → `Radio`; other events are ignored; the deadline → `HandshakeTimeout { phase }`.

**`hold`** loops on `next_event` with no deadline:

- `Frame(f)` from `bssid` with `ETHERTYPE_PAE`: `handle` as above. `Ok(reply)`: send; install `tk` and `gtk` when present, each with its log line; a key the kernel refuses is a warning. `Err(e)`: a warning, and the frame is dropped.
- `Nl(Disconnected { reason, by_ap })` → return `Lost::Disconnected`.
- `Nl(Roamed { .. })` → `disconnect(3)`, return `Lost::Roamed`.
- `Overrun` → `disconnect(3)`, return `Lost::EventsLost`. An error → `disconnect(3)`, return `Lost::Radio(text)`.
- Everything else is ignored.

`run` keeps a `Backoff` and a list of BSSIDs that failed, and repeats this for ever:

1. `report(Scanning)`. `scan`. Then `survey(&results, &cfg.ssid, &failed)`; if it has candidates and every one of them is in the list, clear the list (the order needs no second survey). Log the scan line with `seen` and with candidates plus skipped as the count of the configured name, then one `candidate` line each and one `skipping` line each.
2. No candidate → the attempt fails with `NoCandidate { seen, out_of_scope: skipped.len() }`.
3. `report(Joining { .. })` and `join` with the first candidate.
4. On `Ok(link)`: `report(Joined { .. })`; log the `joined` line with the milliseconds since step 1 began; `hold`; log `link lost`. If the link held for `STABLE_LINK` or longer, `backoff.succeeded()` and clear the list; otherwise add the BSSID to the list.
5. On a failed attempt: log `attempt failed`; if `passphrase_suspect()`, log `the passphrase may be wrong`; if a candidate was tried, add its BSSID to the list.
6. `wait = backoff.failed()`. If it is not zero: `report(Waiting { secs })`, log `next attempt in {n} s`, sleep.
