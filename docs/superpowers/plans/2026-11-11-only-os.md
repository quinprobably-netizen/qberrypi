# Milestone 8: qberrypi as the only system, with network updates — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. One
> fresh implementer per task, in order; no per-task review (owner: lean process). Steps use
> checkbox (`- [ ]`) syntax.

**Goal:** a card that holds qberrypi alone in two slots, a trial boot with automatic rollback,
an authenticated update route, and `xtask image | update | backup-card | flash`, with QEMU
scenarios and docs.

**Spec (binding):** `docs/superpowers/specs/2026-11-11-qberrypi-only-os-design.md`, read it whole
first. Also binding: the hard rules of `2026-11-11-qberrypi-watchdog-design.md` and ruling 17 of
`docs/superpowers/plans/2026-11-10-execution-order.md` (latency).

**Tech stack:** Rust 2024; tokio current-thread runtime with the blocking pool of five
(`services::blocking`); rustls 0.23 (`rustls-rustcrypto` on the Pi; xtask may use the `ring`
provider, as qberrypi's tests already do); `fatfs` 0.3 (MIT) already in xtask. New crates only
if a task says so; check any new crate's licence (no GPL/AGPL/LGPL; MIT, Apache-2.0, BSD, ISC,
Zlib, Unicode are fine) and say so in the commit message.

## Global constraints (every task)

- Worktree `~/Work/qberrypi-ota`, branch `ota`. `export TMPDIR=~/Work/qberrypi-ota/target/tmp`
  (mkdir it). Never read or write anything under `~/Work/qberrypi/` except through the
  `vendor-cache` symlink, read-only: never run `cargo xtask fetch` or `fetch-lists` (they write
  there). Never touch the dummy `qberrypi.toml` except to read it.
- **No latency regression.** Nothing new runs on the runtime thread for more than a few system
  calls; card I/O, hashing and TLS go on the blocking pool; nothing holds the resolver's lock or
  `dns/` state while waiting. Do not change `dns/` or `qb-dns`.
- **Card writes:** only those the spec's "Card writes, amended" lists. A boot with no marker
  writes nothing (the existing permanent QEMU scenario's byte-identical check must still pass).
- **Privacy, public repo:** tests use 192.0.2.x, 127.0.0.1, example.org, 02:00:00:… MACs. No log
  line names a client address, a file's bytes, a sid, a password or a value from
  `qberrypi.toml`.
- **Never** open a real block device, never run `sudo`, never contact the Pi, no network in
  tests beyond loopback. No `git add -A`/`.`; stage by name. No push.
- `unsafe` only in `crates/qberrypi/src/sys.rs`.
- House style: doc comment on every item, full sentences, bounds and failure modes stated;
  tests named as sentences. Read the neighbouring code first and match it.
- **Gates before every commit:** `cargo test --workspace`; `cargo clippy --workspace
  --all-targets` with 0 warnings; `cargo fmt --all --check`; `cargo build -p qberrypi --release
  --target aarch64-unknown-linux-musl`; `grep -rln unsafe crates/qberrypi/src crates/qberrypi/tests`
  prints only `crates/qberrypi/src/sys.rs`. A commit touching `init.rs` or `xtask/` also runs
  `cargo xtask build && cargo xtask qemu-test` with every scenario ok (check
  `pgrep -x qemu-system-aar` for leftovers first and after).
- Commit message ends with a `Co-Authored-By: <your own model name> <noreply@anthropic.com>`
  trailer naming the model that wrote the commit.
- At the end of your task, append 3–6 lines to `.superpowers/sdd/2026-11-11-only-os/progress.md`
  (commit hash, what was done, anything deferred or surprising).

## Rulings made by this plan

1. Boot firmware comes from a new pin (`raspi-firmware_1.20260915-1_all.deb`, trixie,
   SHA-256 `56b6f8792fb27bcc22f101a5a0d27af637e0d13e85dfc0fde5ff140abc929b0f`, SHA-512
   `4558b24a88ecbd29b10eca8d18d6852791d19b823f7cc964fd384761c56aab20670ae008595b8d428a8794c2c13efe4dd343adff7866298d265d3ef7106bd8d2`),
   not `vendor-cache/extracted/firmware` (that is the Wi-Fi firmware). Files under
   `usr/lib/raspi-firmware/`: `bootcode.bin`, `start.elf`, `fixup.dat`, `LICENCE.broadcom` →
   `vendor-cache/extracted/boot/`. The session lead runs `cargo xtask fetch` after the merge. A
   copy for local tests is at `target/tmp/fw/x/usr/lib/raspi-firmware/` (not committed).
2. Firmware `tryboot` is the default trial; the software trial is `--software-trial`.
3. A slot's identity is `qberrypi.slot=a|b` on the kernel command line; selection is copying
   `qberrypi-X/config.txt` over `config.txt` in place.
4. Image 256 MiB, FAT32; private outputs under git-ignored `private/` (0700 dir, 0600 files).
5. The update body is one request: length-prefixed manifest, then the files in order.
6. Health for the confirm: ≥ 120 s since init started, associated, clock set, ≥ 1 forwarded
   answer from an upstream (self-query `example.org A` over loopback if none). Trial limit 600 s.
7. New faults `trial_panic` and `trial_stall` act only on a trial boot.
9. The update body sends `cmdline.txt` and `config.txt` first (each at most 4 KiB, held in
   memory), then the other eight in `SLOT_FILES` order; the receiver refuses any other order, so the
   slot-name and `kernel_change` checks are made before a byte reaches the card.
8. QEMU trials confirm with `debug.trial_offline = true` and `debug.trial_confirm_secs`; both
   are development switches that `deploy --permanent`, `image` and `update` refuse.

### Task 1: `slots` — the layout, the marker, the selection and the boot rules (pure)

**Files:** create `crates/qberrypi/src/slots.rs`; modify `crates/qberrypi/src/lib.rs`.

Everything here is a pure function or works on a directory standing for the mounted boot
partition; nothing calls it yet.

- [ ] `enum Slot { A, B }` with `other()`, `letter()`, `dir()` (`"qberrypi-a"`), `from_cmdline(&str)
  -> Result<Option<Slot>, String>` (`None` when no `qberrypi.slot=` token; an error for any value
  but `a`/`b` or two tokens).
- [ ] `SLOT_FILES: [&str; 10]` in the spec's order; `BOOT_FILES` (all but `initramfs8`,
  `qberrypi.toml`, `tls.pem`).
- [ ] `selected_slot(config: &[u8]) -> Result<Slot, &'static str>`: exactly one uncommented
  `os_prefix=` line, naming `qberrypi-a/` or `qberrypi-b/`. `check_slot_config(text, slot)` and
  `check_slot_cmdline(text, slot)` (the latter: exactly one `qberrypi.slot=` token, naming the slot,
  one line).
- [ ] `select(boot: &Path, slot) -> io::Result<Select>`: copy `qberrypi-X/config.txt` over
  `config.txt` in place exactly as `bootpart::restore_pios_config` writes (no truncation first,
  `set_len`, `sync_all`); refuse (nothing written) a source that fails `check_slot_config`;
  `AlreadySelected` writes nothing. Factor the in-place write out of `bootpart` and share it
  rather than copy it.
- [ ] The marker `qberrypi-trial.txt`: `struct Marker { slot, from, build: u64, mode: Mode
  (Tryboot|Software), started: bool, failed: Option<String> }`, `render()`, `parse()` (unknown
  lines ignored; missing keys or `slot == from` an error), `read_marker(boot) ->
  io::Result<Option<Result<Marker,String>>>`, `append_line(boot, line)` with `sync_all`,
  `remove_marker(boot)`. A `failed=` reason is one line, at most 200 bytes, control characters
  dropped.
- [ ] `enum BootAction { Normal, NormalWarnTryboot, Trial { marker, select_from_first: bool },
  ConfirmInterrupted, SecondTrialBoot, RolledBack { marker }, BadMarker(String) }` and
  `decide(me: Slot, selected: Slot, marker: Option<Result<Marker,String>>) -> BootAction`,
  exactly the spec's table. Test every row.
- [ ] `boot_files_digest(entries: impl IntoIterator<Item=(&str, &[u8])>) -> String`: hex SHA-256
  over `"<sha256hex>  <name>\n"` lines sorted by name for the names in `BOOT_FILES`, with
  `config.txt` and `cmdline.txt` first normalised to slot a (replace the slot's `os_prefix` value
  and the `qberrypi.slot=` value). Same digest for the a and b forms of one build; a different one
  when any boot file differs; an error if a `BOOT_FILES` name is missing.
- [ ] Unit tests in the file for all of the above (tempdirs; refusals leave files byte-identical
  and mtimes unchanged, as `bootpart`'s tests do).

**Acceptance:** gates green; `slots` has no dependency on init, services or api.

### Task 2: init on a slot card — identity, own folder, the boot rules, the tryboot restart

**Files:** modify `crates/qberrypi/src/init.rs`, `bootpart.rs`, `sys.rs`, `supervisor.rs`,
`config.rs` (faults only if needed here), `status.rs`; create `crates/qberrypi/src/update/mod.rs`
(the shared state only); modify `xtask/src/build.rs` (the digest file).

- [ ] Step 1 reads `/proc/cmdline` once: `Slot::from_cmdline` (an error is fatal). `bootpart`'s
  readers and `append_log` take the folder (`qberrypi` or `qberrypi-X`) instead of the constant;
  every caller passes the boot's folder.
- [ ] Step 3 on a slot boot, **before `qberrypi.toml` is parsed and before the watchdog**: in the
  read-only mount that reads the configuration, also read `config.txt` (→ `selected_slot`) and the
  marker; `slots::decide`; if the action writes (append `started`, software `select(from)`,
  delete the marker), do it in one writable mount right then, through the existing card claim.
  `SecondTrialBoot` restarts plainly at once (after logging). Log one INFO/WARN/ERROR line per
  action (no file contents). On a slot boot the Raspberry Pi OS restore is never attempted, in
  step 4 or in `fatal`'s rescue.
- [ ] `update::UpdateCtl` (shared, `Arc`): `slot: Option<Slot>`, `boot_files: Option<String>`
  (read from the initramfs file below), state `Idle | Receiving | Trial{marker, began: Instant,
  waiting_for}`, `last: Option<Outcome{confirmed|rolled_back, build, detail}>`, a `busy` try-lock
  for the receiver, and `restart: watch::Sender<Option<Restart>>` with `Restart::{Tryboot, Plain(reason)}`.
  The boot rules fill `state`/`last` (a rollback sets `last` with the spec's `detail` wording).
- [ ] `supervisor::Plan` gains the restart receiver; `run` ends with a new `Reason::Restart(Restart)`
  when it changes to `Some`. `leave`/`wind_down` log it at INFO for an update and ERROR for a
  give-up; the caller then calls `sys::reboot()` or a new `sys::reboot_tryboot()`
  (`libc::syscall(SYS_reboot, LINUX_REBOOT_MAGIC1, LINUX_REBOOT_MAGIC2,
  LINUX_REBOOT_CMD_RESTART2, c"0 tryboot")`, after `sync()`, falling back to the same wait as
  `reboot`).
- [ ] `status.rs` `/api/v1/stats` gains `slot`, `boot_files`, `update` exactly as the spec
  says (`null`s on the old layout). A test for each shape.
- [ ] `xtask build` packs `etc/qberrypi/boot-files` (the hex digest of `slots::boot_files_digest`
  over the build's kernel, dtb, overlays and the slot-a forms of `config.txt` and `cmdline.txt`
  that Task 4's slot builder will produce — put `slot_config_txt(slot)`/`slot_cmdline_txt(slot)`
  in `xtask/src/build.rs` next to `CONFIG_TXT`/`CMDLINE_TXT` now, so both use one source). The
  slot config's first comment line says how slots are selected, not Raspberry Pi OS.
- [ ] Tests: init's helpers are tested the way init's existing ones are (fake `Card`, pure
  functions); the old-layout path is unchanged (existing tests pass untouched).

**Acceptance:** gates incl. QEMU (all existing scenarios still ok: the old layout is untouched).

### Task 3: the trial — confirm, give up, and the two faults

**Files:** create `crates/qberrypi/src/update/trial.rs`; modify `init.rs` (a component),
`config.rs`, `fault.rs`, `xtask/src/deploy.rs` (`refuse_development_switches`).

- [ ] Config: `debug.trial_confirm_secs` (0 = default 120; 1..=3600), `debug.trial_offline`
  (bool), faults `"trial_panic"` and `"trial_stall"`. `refuse_development_switches` refuses the
  two new keys when set and both faults (they are faults). `qberrypi.example.toml` documents them
  under `[debug]` as development switches.
- [ ] A supervisor component `trial`, present only while `UpdateCtl` is on trial. It waits on
  timers and the existing watches (Wi-Fi status, clock synced) and copies one number out for the
  upstream answers (the same accessor `/api/v1/stats` uses); it keeps `waiting_for` current. After
  `confirm_secs − 10 s` with no forwarded answer yet it sends one `example.org A` query to
  127.0.0.1:53 over UDP (5 s timeout, every 10 s). When healthy and the time has come: on the
  blocking pool, through init's card claim, `slots::select(me)` then `remove_marker`; on success
  `last = confirmed`, `state = Idle`, INFO `update: build N confirmed on slot X`. A failed write is
  an ERROR and is retried every 30 s until the limit. At 600 s unconfirmed: append
  `failed=<reason>` (best effort) and send `Restart::Plain`.
  With `trial_offline`, `wifi`/`clock`/`upstream` are not waited for.
- [ ] `trial_panic`: on a trial boot only, panic 3 s after the supervisor starts (through the
  fault component, so the existing panic path restarts the board). `trial_stall`: on a trial boot
  only, the existing stall behaviour. Both do nothing on a boot that is not on trial.
- [ ] Tests with a paused tokio clock and fakes for the card and the health inputs: confirms at
  120 s and not before; waits while any input is missing; self-query only when no answer came;
  gives up at 600 s with the reason; a failed confirm write is retried; the faults act only on
  trial. A test that the component never blocks the runtime (no blocking call outside
  `services::blocking`).

**Acceptance:** gates incl. QEMU.

### Task 5: the update receiver (`POST /api/qbp/update`)

**Files:** create `crates/qberrypi/src/update/receive.rs`; modify `crates/qberrypi/src/api/http.rs`
(head and body split), `api/mod.rs` (the connection loop), `api/routes.rs` (a session check the
connection can call), `services.rs` (hand `UpdateCtl` and the card to the API), `init.rs` (the
card it is given: the real card through the claim).

- [ ] `http`: `read_head` returns the head with its `Content-Length`; `read_request` keeps its
  4 KiB cap for every other request (existing tests unchanged). The connection loop recognises
  `POST /api/qbp/update` from the head, checks the session (401 without a valid one, before any
  body byte is read; another method on the path is 405), and hands the stream to the receiver
  with its own bounds (64 MiB, 10 min from the head, 30 s per read, set on the `Deadlined`
  socket). After it, the connection closes.
- [ ] `update::receive`: the spec's body format, refusals, write order, verification on a fresh
  read-only mount, `tryboot.txt`/selection, the marker last, the 200 reply, then the restart
  request one second later (`Restart::Tryboot` or `Plain` for software mode). The card is a trait
  (`with_card(access, work)`), real in init, a tempdir in tests. Only one at a time (`busy`);
  refused on trial or with no slots. The manifest's names must be exactly `SLOT_FILES`; sizes sum
  to the body length; hex is 64 lowercase digits.
- [ ] Logging per the spec, nothing else.
- [ ] Host test end to end (in `update/receive.rs` or `services.rs`'s tests, beside the existing
  API-over-TLS tests): a real TLS connection with the pinned test client, login, upload of ten
  small fake files to a tempdir card on slot a → slot b written, verified, `tryboot.txt` equals
  slot b's `config.txt`, marker as rendered, restart requested with `Tryboot`; software mode
  selects b in `config.txt` instead. Refusals: no sid (nothing read), busy, not newer, wrong slot,
  kernel change, bad names, a hash that does not match (a fake card that flips a byte on the
  re-read), over the cap, a client that stops sending (deadline). While a 32 MiB upload streams,
  DNS answers from the cache over UDP and the runtime's longest gap stays under the bound the
  existing API tests use; print the gap.

**Acceptance:** gates incl. QEMU.

### Task 8: QEMU — boot slots like the firmware, three trial scenarios

**Files:** modify `xtask/src/qemu.rs` (and `sdimage.rs` readers if needed).

- [ ] A firmware stand-in: from the image, read `config.txt`, or `tryboot.txt` when the last
  restart's console line was `reboot: Restarting system with command '0 tryboot'`; take its
  `os_prefix` slot; extract that slot's kernel, dtb, initramfs to the scenario folder; kernel
  arguments = the scenario's QEMU arguments plus the slot's `qberrypi.slot=`. A scenario may run
  up to N boots: a restart request or a halted guest (`GUEST_HALTED`, which a panic reaches without
  the watchdog driver) ends one boot and starts the next from the image as the guest left it.
  Document this in the module doc beside `RESTART_UNCHECKED`.
- [ ] Slot images built with Task 4's `sdimage`/slot code (fake firmware files are fine, QEMU does
  not run them), each slot's `qberrypi.toml` edited from the example as the existing scenarios do
  (`log_to_sd = true`, `return_after_secs`, `trial_offline = true`, `trial_confirm_secs = 5`).
- [ ] Scenarios: **trial confirms** (tryboot.txt + marker for b, first boot in tryboot mode: b
  confirms, returns; second boot comes up on b without a trial; card: `config.txt` == b's, no
  marker, b's log has the confirm line); **trial fails, firmware** (b with `trial_panic`: panics;
  the next boot is a, which logs the rollback with `the trial build restarted before it
  confirmed` and deletes the marker; `config.txt` still selects a); **trial fails, software**
  (`config.txt` selects b, marker mode software: b selects a first, panics; a rolls back). Each
  with the house's "no unexpected complaint" checks and its own allowances.
- [ ] Unit tests for the stand-in (which file it reads, the slot it picks, the arguments) and the
  scenarios' config edits.

**Acceptance:** gates; `cargo xtask qemu-test` with every scenario ok, old and new; record the

### Task 10: cheap, secure boot-speed wins (added 2026-11-12, owner-approved)

Measured at the cutover boot: first client answer 5.9 s after the kernel started; the Wi-Fi scan
took 2.8 s of it (qbp time 0.74 → 3.57, two BSSIDs of the SSID, 5180 and 2437 MHz); association,
handshake and keys 0.14 s; address to first answer 0.1 s.

**Files:** `crates/qberrypi/src/wifi/` (the scan request only), `config.rs`, `status.rs`,
`qberrypi.example.toml`, `xtask/src/build.rs` (slot config/cmdline), `xtask/src/image.rs`,
`xtask/src/update.rs`, `docs/bring-up/m8-only-os.md`.

- [ ] `[wifi] hint_mhz = [5180, …]`: optional, at most 4 entries, each a valid 2.4/5 GHz channel
