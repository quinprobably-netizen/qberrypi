# Milestone 6 (Cutover) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** qberrypi stays selected across restarts and pulled power and answers DNS for the whole home network, with a safe, documented way back to Raspberry Pi OS through the PC's card reader.

**Architecture:** `deploy --permanent` refuses development switches, waits out Raspberry Pi OS's package manager, and after the restart waits for qberrypi itself to answer. qberrypi carries its own copy of the screen's overlay, so a Raspberry Pi OS upgrade cannot darken the panel. `cargo xtask return-to-pios` performs the way back on a card mounted on the PC, with init's own restore code. The DNS listener counts client addresses so that the cutover can be seen to reach every device; only the counts are shown on the open status port, and the recent-query list leaves it. `cargo xtask boot-time` measures power-on to first answer from outside.

**Tech Stack:** Rust stable, edition 2024; no new dependency. The firmware's `overlay_prefix`; the overlay files from the pinned kernel package.

**Spec:** `docs/superpowers/specs/2026-11-10-qberrypi-cutover-and-api.md`, part 1, together with `docs/superpowers/specs/2026-11-10-qberrypi-design.md` (Success criteria, Sharing the card, One-shot boots, Status, Failure handling). Rulings 1–16 of `docs/superpowers/plans/2026-11-10-execution-order.md` bind this plan; ruling 15 makes every `piscreen` line `rotate=270`, and ruling 16 records the owner's answers this plan follows.

**Starts when:** milestones 1–5 are merged into `qbp-v1` with their Pi checks passed. Every name below that is not defined here is from the Interfaces blocks of `2026-11-10-m1-wifi.md`, `2026-11-10-m2-m3-resolver-blocker.md` and `2026-11-10-m4-m5-resilience-panel.md`. By ruling 5, where a name was built differently, the built one stands and this plan's steps follow it.

## Global Constraints

- `unsafe` only in `crates/qberrypi/src/sys.rs`.
- No secret in a log line, an error, `Debug` output, `/log`, the status JSON or a committed file. The repository is public: examples use `192.0.2.0/24`, `198.51.100.0/24` and names under `example.com` or `.invalid`; no real network name, address, MAC address or SSH alias is committed (the Pi is `<alias>`, its address `<address>`). Bring-up notes carry no network name, address or raw log.
- Per-query and per-device data are not served on port 80: no queried name and no client address in any port-80 answer, `/log` included. The totals stay open.
- The card is written only by `debug.one_shot`, `debug.log_to_sd`, and a fatal error before the configuration was read. This plan adds no write and no new moment at which one happens (milestone 4/5 Task 10's host test and QEMU scenario keep passing unchanged).
- The initramfs holds exactly one executable, `/init`, and it never runs another program. Every file the boot folder gains comes from a pinned, checksummed package through `xtask/src/pins.rs`.
- One runtime (ruling 1); nothing holds its thread for more than about 50 ms.
- Implementers never reach the Pi: no `ssh`, no `deploy`. Every Pi step is the session lead's, on a build that has just passed `qemu-test`, with the owner, and each deploy takes the household's DNS away for one to four minutes.
- Clean before every commit, with no warnings: `cargo test --workspace`, `cargo clippy --workspace --all-targets`, `cargo fmt --all --check`, `cargo build -p qberrypi --release --target aarch64-unknown-linux-musl`. A task that touches `init.rs`, `modules.rs`, `dns/` or `xtask/` also runs `cargo xtask build && cargo xtask qemu-test`, and every scenario passes.
- Git: stage files by name (never `git add -A` or `git add .`). Every commit message ends with a `Co-Authored-By:` trailer naming the model that wrote the commit, for example `Co-Authored-By: Claude Fable 5.2 <noreply@anthropic.com>`. Never push.

## Review Focus

1. `return-to-pios` is pointed at the wrong place — the home directory, a USB stick, the card's root partition, the boot partition of another card, a path that does not exist: it refuses and writes nothing. (Test in Task 4.)
2. The card's `config.pios.txt` is missing, empty, holds a NUL byte or itself selects qberrypi, or the card is mounted read-only: `return-to-pios` says why, and `config.txt` is unchanged. (Test in Task 4.)
3. The Pi is back on Raspberry Pi OS after weeks away and its package manager starts upgrading when a deploy arrives: the deploy refuses before writing anything and says to try again. (Test in Task 1.)
4. A permanent deploy of a `qberrypi.toml` that still has a development switch on (one-shot, card log, a return time, touch calibration, a provoked fault) is refused before anything is copied. (Test in Task 1.)
5. Many source addresses (a scan, a busy network, more than 256 devices) reach port 53: the client table stays at 256 entries, drops the least recently seen, never counts `127.0.0.0/8`, never shows an address on port 80, and answering a query never waits on it. (Tests in Task 3.)

## Decisions the spec leaves open

| Subject | Decision | Task |
|---|---|---|
| What counts as the boot partition | `bootcode.bin`, `config.txt` and `config.pios.txt` files and a `qberrypi` directory directly in `--boot`. Anything else is refused before any write. | 4 |
| Syncing on the PC | `File::sync_all` on `config.txt` and on the directory, then a read-back with `cmp` semantics; the tool tells the owner to eject the card, and does not unmount it itself. | 4 |

| Package manager guard | The script refuses (status 11, `upgrading`) while `pgrep -x` finds `apt`, `apt-get`, `dpkg` or `unattended-upgr` (the kernel's 15-character name of `unattended-upgrades`). It checks before step 2 writes anything, on every deploy. | 1 |
| Overlay names | `overlay_prefix=ov-`; files `ov-README`, `ov-overlay_map.dtb`, `ov-qb-piscreen.dtbo`; `dtoverlay=qb-piscreen,speed=16000000,rotate=270`. | 2 |

| `/api/v1/queries` on port 80 | 403, `text/plain; charset=utf-8`, body `this needs the API login\n`. The query log itself stays in memory for milestone 7. | 3 |
| Boot-time probe | UDP, a fresh ID every 200 ms, answers read without waiting; `qberrypi-snapshot.invalid` A until answered, then `example.com` A until NOERROR with an address; 120 s cap. | 5 |

`check_local` with `permanent`, in this order, each message naming the key and ending `; nothing was copied`:
- `debug.one_shot` on: `"--permanent with debug.one_shot on would return to Raspberry Pi OS at the first restart: turn debug.one_shot off"`
- `debug.log_to_sd` on: `"a permanent qberrypi must not write its log to the card: turn debug.log_to_sd off"`
- `debug.return_after_secs` not 0: `"a permanent qberrypi with debug.return_after_secs set would restart for ever: set it to 0"`
- `debug.calibrate_touch` on: `"debug.calibrate_touch is for one boot of calibration: turn it off"`
- `debug.fault` not `none`: the existing message.

The script, in step 1 after the hardware checks: `for p in apt apt-get dpkg unattended-upgr; do if pgrep -x "$p" >/dev/null 2>&1; then die "$upgrading" "Raspberry Pi OS is installing updates ($p is running); try again when it has finished. Nothing was changed"; fi; done`. The `RemoteScript` gains `upgrading={UPGRADING}`.

`deploy_with`, when `debug.one_shot` is off: in place of today's early return, wait up to `GONE_WITHIN` for SSH to stop answering, then `wait_for_qberrypi` with `build_seen` = `probe::get_stats((net.address.addr, status::PORT), Duration::from_secs(2))` read as `v["build"].as_u64()`. Success prints `deploy: {host}: qberrypi build {n} answers at {address} {s} s after the restart; to return to Raspberry Pi OS later: {WAY_BACK}`. Failure is an error that says the Pi did not answer in time and ends with `To return to Raspberry Pi OS: {WAY_BACK}`. `WAY_BACK` also replaces the card advice in today's permanent message and in `RECOVERY`. A `build` that is another number keeps the wait going.

### Task 4: `cargo xtask return-to-pios`

**Files:**
- Create: `xtask/src/pios.rs`
- Modify: `xtask/src/main.rs`

**Interfaces:**
- Consumes: `qberrypi::bootpart::{restore_pios_config, Restore}` (the function init's one-shot restore runs).
- Produces:

```rust
/// Why a directory is not this Pi's boot partition, or None when it is.
pub fn not_the_boot_partition(boot: &Path) -> Option<String>;
/// Makes the mounted card start Raspberry Pi OS next; the text to print on success.
pub fn return_to_pios(boot: &Path) -> anyhow::Result<String>;
```

Command: `cargo xtask return-to-pios --boot <dir>`.

`not_the_boot_partition`: `Some("<dir> does not exist")`, or `Some("<dir> has no {name}: it is not the Pi's boot partition")` for the first of `bootcode.bin`, `config.txt`, `config.pios.txt` (files) and `qberrypi` (a directory) that is missing.

`return_to_pios`, stopping at the first failure with nothing written:
1. `not_the_boot_partition` → its text, ending `; nothing was changed`.
2. `restore_pios_config(boot)`. `Refused(reason)` → `"{reason}; nothing was changed"`. An I/O error → `"{boot}: {error}"`; a read-only mount ends up here.
3. `Restored`: `sync_all` on `config.txt` and on the directory, then read both files back and compare. A difference → `"config.txt did not read back as config.pios.txt: copy config.pios.txt over config.txt by hand before the card goes back"`.

- Produces:

```rust
pub const ASK_EVERY: Duration = Duration::from_millis(200);
pub const GIVE_UP: Duration = Duration::from_secs(120);
pub const BLOCKED_NAME: &str = "qberrypi-snapshot.invalid";
pub const FORWARDED_NAME: &str = "example.com";
#[derive(Debug, Default, PartialEq)] pub struct BootTimes { pub first: Option<Duration>, pub forwarded: Option<Duration> }
#[derive(Debug, Default)] pub struct Timer { pub times: BootTimes }
impl Timer {
    pub fn asking(&self) -> Option<&'static str>;           // the name to ask next; None when both are known
    pub fn answered(&mut self, at: Duration, answer: &Answer);
}
pub fn report(times: &BootTimes) -> String;
fn ask_until_done(server: SocketAddr, enter: Instant, give_up: Duration) -> io::Result<BootTimes>;
pub fn run(server: Option<Ipv4Addr>, root: &Path) -> anyhow::Result<()>;
```

`Timer::answered`: while asking `BLOCKED_NAME`, any answer (any rcode) sets `first`. While asking `FORWARDED_NAME`, a NOERROR answer with an address that is not `0.0.0.0` sets `forwarded`. Other answers change nothing. `report`: `boot-time: first answer {a:.1} s after power-on; first forwarded answer {b:.1} s` (or `none within 120 s` for a missing one), then `boot-time: target: first answer under 15 s: met` or `: missed`. `run`: prints `boot-time: asking {address}; press Enter at the moment you plug the Pi's power in`, waits for the line, then `ask_until_done`. That function, every `ASK_EVERY`, sends `query(id, name, 1)` with a fresh ID from a nonblocking UDP socket bound to `0.0.0.0:0`, and reads every datagram waiting. Answers whose ID is one of those sent go to `answered`, with the time since Enter. It stops when `asking()` is `None` or after `give_up`. `run` then prints `report`.

Command: `cargo xtask boot-time [--server <ipv4>]`; without `--server`, `net.address` of `./qberrypi.toml`.
